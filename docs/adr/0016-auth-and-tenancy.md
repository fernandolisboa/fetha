# Better Auth for identity; the user account is the tenant

Fetha needs identity from day one: a person registers, verifies their email, accepts the terms of
use and the privacy policy, signs in, stays signed in across the PWA, and signs out. A solo
project cannot afford to hand-roll sessions and email verification securely, and Feudo already
proved the pattern (its ADR-0001). We use Better Auth with the Drizzle adapter on Neon Postgres,
the same library and module shape as Feudo, **without the organization plugin**: Fetha has no
households, no shared workspaces and no roles. The tenant is the user account (CLAUDE.md,
CONTEXT.md).

## Decision

**Identity (Better Auth, Drizzle adapter on Neon Postgres, emails through Resend)**

- Email + password with mandatory email verification (`requireEmailVerification`). Magic link and
  password reset are out of scope for this ticket (#10) but nothing here precludes adding them:
  Better Auth's plugin API composes without touching the tables or hooks below.
- Rate limiting is out of scope for this ticket (#10); Better Auth's defaults apply until then.
- `REGISTRATION_MODE=open|invite|closed` (`@fetha/contracts`) is read at request time inside a
  `hooks.before` middleware on `/sign-up/email`: `closed` refuses every sign-up; `invite` allows
  sign-up only for an email that holds a row in `invites` with `consumed_at` null; `open` allows
  any sign-up. The default is `invite`.
- Better Auth's tables (`user`, `session`, `account`, `verification`) are generated by its CLI
  (`pnpm --filter @fetha/web db:auth-schema`) into `src/db/schema/auth.ts` and migrated with
  drizzle-kit like every other table. Only `src/modules/auth` and `src/lib/user-scoped-repository`
  touch Better Auth directly; the rest of the code sees a session with `userId`, `name`, `email`
  through `getSession()` / `requireUser()`.
- Terms and privacy acceptance is **not** a Better Auth additional field (Feudo's choice); it is
  its own table, `terms_acceptances` (`user_id`, `terms_version`, `accepted_at`), written by a
  `databaseHooks.user.create.after` hook right after the user row is created. This keeps a full,
  append-only history if the terms version changes later, and gives the ticket's required
  isolation test a table to isolate.
- `invites` (`id`, `email` unique, `created_at`, `consumed_at`, `consumed_by_user_id`) is shared,
  admin-managed data: not user-scoped, read and written only from the sign-up hook and from
  `createInvite`, a server action that requires an authenticated session (`requireUser()`). The
  first invite (the owner's own) has no existing session to grant it, so it is seeded directly
  with `scripts/seed-invite.mjs` against the target database.

**Tenancy (user account, no households)**

- Every domain table this ticket adds is scoped by `user_id` and reached only through a
  user-scoped repository built on `UserScopedRepository`
  (`src/lib/user-scoped-repository.ts`): the constructor takes `(db, userId)` from the session,
  and no method may accept a user id as a parameter. `TermsAcceptanceRepository` is the first
  concrete repository and the first isolation test (`terms-acceptance-repository.integration.test.ts`).
  Every future module reuses this base.
- Reference data, the catalog and shared strategies (ADR-0012) remain the only read-only
  exceptions to tenant scoping (CLAUDE.md, principle 5); `invites` is a third, narrower exception
  for the same reason Better Auth's own tables are: it has no owning user until consumed.

**Email (`Mailer` port, `src/modules/auth/email/`)**

- `Mailer.send(input)` is the interface. `ResendMailer` is the production adapter, selected only
  when `VERCEL_ENV === "production"`. Every other deployment (local dev, Vercel preview, CI) uses
  `CaptureMailer`, which writes the email into `mail_outbox` instead of sending it — Vercel
  functions are separate processes, so this is also how Playwright, running against a preview
  deployment, gets the verification link back: an E2E-only route
  (`/api/e2e/verification-link`) reads the latest `mail_outbox` row for an email and returns 404
  unless the request carries `E2E_SECRET` and the deployment is not production. `FakeMailer`
  (in-memory, no I/O) is available for unit tests that construct `buildAuthOptions` directly and
  do not need a database.
- This differs from Feudo's `EMAIL_PROVIDER` env switch: Fetha selects the mailer from the
  deployment environment (`VERCEL_ENV`) rather than an explicit flag, because "capture instead of
  send" needs to be true for every non-production deployment, not opt-in per environment.

**CI database**

- Integration tests run against a single, shared, long-lived Neon development branch, not a
  fresh preview branch per PR (deviation from Feudo, which resets its preview branch between
  tests). The GitHub secret `DATABASE_URL_PREVIEW` points at that branch. CI runs
  `drizzle-kit migrate` against it before the integration job, and every integration test creates
  rows with a unique, randomly suffixed email and deletes them in `afterEach`; no test resets the
  schema or truncates a table it does not own.

## Considered options

- **Better Auth's `organization` plugin, mapped to nothing** (Feudo's shape unchanged): rejected;
  Fetha has no concept a household or org would model, and carrying unused membership tables and
  role checks would violate YAGNI for no benefit.
- **Terms acceptance as Better Auth `user` additional fields** (Feudo's choice): rejected for
  Fetha; a dedicated table gives an append-only history across terms versions and doubles as the
  first isolation-tested user-scoped table the ticket asks for.
- **`EMAIL_PROVIDER` env switch** (Feudo's choice): rejected in favor of deriving the mailer from
  `VERCEL_ENV`, since every non-production deployment must capture, not just tests.

## Consequences

- Better Auth's vocabulary (`user`, `session`) appears in `src/db/schema/auth.ts` and `options.ts`
  only; the rest of the app imports `CurrentUser` from `src/modules/auth`.
- "Every domain table carries `user_id`" (CLAUDE.md) holds without exception here; `invites` is
  data about an email address, not about a user, so it does not carry one until consumed.
- Magic link, password reset and rate limiting (#10) add plugins and hooks to
  `options.ts` without touching the schema or the repository pattern established here.
