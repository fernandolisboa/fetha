# Better Auth for identity; the user account is the tenant

Fetha needs identity from day one: a person registers, verifies their email, accepts the terms of
use and the privacy policy, signs in, stays signed in across the PWA, and signs out. A solo
project cannot afford to hand-roll sessions and email verification securely, and Feudo already
proved the pattern (its ADR-0001). We use Better Auth with the Drizzle adapter on Neon Postgres,
the same library and module shape as Feudo, **without the organization plugin**: Fetha has no
households, no shared workspaces and no roles. The tenant is the user account (CLAUDE.md,
CONTEXT.md).

This ADR was revised during the review pass on ticket #9 (fix-forward, this same date): terms
acceptance moved from its own history-only table to a Better Auth additional field so consent is
atomic with the user row, the CI database topology and reset procedure were specified, the mailer
selection rule and E2E secret comparison were hardened, and the invite-mode sign-up response was
made generic to avoid email enumeration. The "Decision" section below reflects the final shape;
superseded choices are called out inline.

Magic link, password reset and database-backed rate limiting, called out below as out of scope for
ticket #10, were built by that ticket. See ADR-0018, which amends this one with those decisions
rather than editing the sections below in place.

## Decision

**Identity (Better Auth, Drizzle adapter on Neon Postgres, emails through Resend or capture)**

- Email + password with mandatory email verification (`requireEmailVerification`). Magic link and
  password reset are out of scope for this ticket (#10) but nothing here precludes adding them:
  Better Auth's plugin API composes without touching the tables or hooks below.
- Rate limiting is out of scope for this ticket (#10); Better Auth's defaults apply until then.
- `REGISTRATION_MODE=open|invite|closed` (`@fetha/contracts`) is read at request time inside a
  `hooks.before` middleware on `/sign-up/email`: `closed` refuses every sign-up; `invite` allows
  sign-up only for an email that holds a row in `invites` with `consumed_at` null; `open` allows
  any sign-up. The default is `invite`. `registrationModeSchema` treats an empty string the same
  as unset (some deployment tooling leaves env vars set-but-empty rather than absent).
- Better Auth's tables (`user`, `session`, `account`, `verification`) are generated by its CLI
  (`pnpm --filter @fetha/web db:auth-schema`) into `src/db/schema/auth.ts` and migrated with
  drizzle-kit like every other table. `@better-auth/cli` is invoked through
  `pnpm dlx @better-auth/cli@1.4.22`, an exact pin, never `@latest` — but still not a devDependency
  of `apps/web`: its own published versions (latest stable `1.4.22`) trail `better-auth` (`1.7.3`)
  and depend on an older `better-call`/`@better-auth/core`. Adding it to `apps/web`'s
  `devDependencies` and invoking it with `pnpm exec` — the fix-forward reviewer's first choice —
  was tried and reverted: `pnpm install` itself succeeds, but the sibling installation corrupts
  pnpm's peer resolution for the _workspace's own_ `@better-auth/core@1.7.3` (it resolves
  `better-call@1.1.8`, pulled in by the CLI's dependency tree, instead of the `^1.4.0` `better-auth`
  1.7.3 actually needs), so loading `auth-schema-config.ts` — which imports the app's own
  `better-auth` instance — throws `SyntaxError: The requested module 'better-call' does not
provide an export named 'kAPIErrorHeaderSymbol'` before the CLI ever reads `DATABASE_URL`.
  `pnpm dlx` installs the CLI into its own isolated store, outside the workspace's dependency
  graph, so it never touches that peer resolution; `auth-schema-config.ts` is still loaded from
  `apps/web` and still resolves the workspace's `better-auth@1.7.3` correctly. Confirmed against
  the real install both ways, not assumed: `pnpm exec better-auth generate …` throws the
  `SyntaxError` above; `pnpm dlx @better-auth/cli@1.4.22 generate …` succeeds. Only `src/modules/auth`
  and `src/lib/user-scoped-repository` touch Better Auth directly; the rest of the code sees a
  session with `userId`, `name`, `email` through `getSession()` / `requireUser()`.
- **Terms and privacy acceptance is a Better Auth `user.additionalFields` pair**:
  `termsVersion` (string) and `termsAcceptedAt` (date), both `input: false` so a client can never
  set them directly. `databaseHooks.user.create.before` stamps both from the current terms version
  and the creation time on every user create, merging them into the same INSERT Better Auth issues
  — a user row can never exist with a null `termsVersion`, because the column is `not null` and
  the value is supplied before the row exists, not after. This **supersedes the original
  decision** in this ADR to keep terms acceptance only in a separate table (Feudo's shape): that
  table remains, but as an append-only history, not the source of truth for "did this user ever
  accept terms" — the `user` row itself is. `databaseHooks.user.create.after` still writes a row to
  `terms_acceptances` (`user_id`, `terms_version`, `accepted_at`) for a full history across future
  terms versions; if that write fails, it is logged and swallowed
  (`recordTermsAcceptanceHistory`), never undoing or failing the registration that already
  succeeded, because the consent of record already lives on `user`.
- `invites` (`id`, `email` unique, `created_at`, `consumed_at`, `consumed_by_user_id`) is shared,
  operational data (see "Operational tables" below), read and written from application code only
  through `hasPendingInvite` and `consumePendingInvite` (`src/modules/auth/invite-repository.ts`),
  both called from the sign-up hook. `databaseHooks.user.create.after` calls
  `consumePendingInviteSafely`, not `consumePendingInvite` directly: the user row already exists
  by the time this hook runs, so a transient failure to mark the invite consumed is logged and
  swallowed, the same guarded log-and-continue shape as `recordTermsAcceptanceHistory` — it must
  never undo or fail a registration that already succeeded. There is no admin action yet that
  creates an invite (YAGNI:
  no admin UI ticket exists), so no repository function for that exists either — fix-forward on
  this ticket's review pass removed the upsert `createInvite` function (created/reopened/left
  untouched, every call reporting which) along with its dead `createInviteAction`, since neither
  had a caller. The first invite (the owner's own) and every invite after it, until an
  invite-management ticket lands, are seeded by hand with `scripts/seed-invite.mjs`, which is now
  the sole implementation of that three-way upsert logic, directly in SQL since scripts in this
  repo stay plain JS with no TypeScript build step — it is not a mirror of a repository function
  anymore, it is the only one.
- **No enumeration on sign-up in `invite` mode**: an email with no pending invite gets the exact
  same outward response as a real sign-up — `signUp()` (`src/modules/auth/service.ts`) maps the
  `invite_required` API error to the same generic `{ status: "ok" }` outcome, and the UI shows the
  same "check your email" screen either way. No user is created and no email is sent, but nothing
  observable from outside distinguishes "invited" from "not invited" at this endpoint.

**Tenancy (user account, no households)**

- Every domain table this ticket adds is scoped by `user_id` and reached only through a
  user-scoped repository built on `UserScopedRepository`
  (`src/lib/user-scoped-repository.ts`): the constructor takes `(db, currentUser)` — the session
  type `CurrentUser`, not a bare string — and no method on a subclass may accept a user id as a
  parameter. `Repository.forCurrentUser(db)` was tried as a static factory on
  `UserScopedRepository` itself but reverted (fix-forward on ticket #11's review pass): it needed a
  lazy `import("@/modules/auth/session")` inside `lib/` to avoid a class-initialization cycle with
  `options.ts`, which wires repositories whose `extends UserScopedRepository` clause needs the base
  class already fully evaluated. The factory now lives where the cycle cannot occur:
  `modules/auth/session.ts` exports `forCurrentUser(db, Repository)`, which calls `requireUser()`
  and constructs `new Repository(db, user)`; `lib/user-scoped-repository.ts` stays pure, importing
  only the `CurrentUser` type. `forCurrentUser` is how every call site outside a Better Auth hook is
  expected to bind a repository to the live session; `databaseHooks.user.create.after` is the one
  exception, since it runs before any session exists and constructs `TermsAcceptanceRepository`
  directly from the just-created user's identity. `TermsAcceptanceRepository` is the first concrete
  repository and the first isolation test (`terms-acceptance-repository.integration.test.ts`).
  Every future module reuses this base.
- Reference data, the catalog and shared strategies (ADR-0012) remain the only read-only
  exceptions to tenant scoping (CLAUDE.md, principle 5); `invites` and `mail_outbox` are a third
  class, described below.
- A child table can carry no `user_id` of its own as long as every read and write reaches it only
  through an already-scoped parent row: `strategy_versions` (#17) has no `user_id` column, but
  `StrategiesRepository` never selects from it except by a `strategy_id` obtained from a
  `strategies` row already filtered by `user_id` (`findMine`) or by visibility (`findShared`), so
  the parent lookup is the access check. This is narrower than the read-only reference-data
  exception above: `strategy_versions` is regular, per-user, mutable-by-insert domain data: it
  costs a second row read where a denormalized `user_id` would cost a column, chosen here because
  a version can never be read, listed or created except through its strategy.

**Operational tables (`invites`, `mail_outbox`): unscoped, system-written, not user data**

Not every table without a `user_id` is reference data. `invites` and `mail_outbox` are a distinct,
narrower exception: they are not shared content a user reads (like the catalog), they are
mechanism the system uses to run itself, and only the system writes them — never a user action:

- `invites` is written by the seed script (bootstrapping) and by the sign-up hook
  (`consumePendingInvite`), and read by the sign-up hook (`hasPendingInvite`). No user-facing
  action reads or writes it: `createInviteAction` and the `createInvite` repository function it
  called were removed as dead surface with no caller — YAGNI until an invite-management ticket
  exists.
- `mail_outbox` exists only because Vercel functions are separate, stateless processes: it is how
  `CaptureMailer` hands a verification link to the E2E-only route
  (`/api/e2e/verification-link`) running in a different invocation. **It is empty in production**
  — `CaptureMailer` is refused outright against a database whose host exactly matches the real
  production Neon pooler host (`CaptureMailerRefusedInProductionError`), so captured email can
  structurally never accumulate there. Every row is single-use and short-lived even outside production: reading the
  latest link for an email (`findLatestVerificationLink`) deletes the row in the same call, and
  every `CaptureMailer.send()` purges anything older than a day before inserting.

**Email (`Mailer` port, `src/modules/auth/email/`)**

- `Mailer.send(input)` is the interface. `ResendMailer` is the production adapter; `CaptureMailer`
  writes into `mail_outbox` instead of sending, for local dev, Vercel preview and CI. Selection is
  by an explicit `MAILER=resend|capture` env var when set; otherwise it defaults to `resend` only
  when `VERCEL_ENV=production` and to `capture` everywhere else (`getMailer`, in
  `src/modules/auth/email/select.ts`). This **supersedes the original decision** to select purely
  from `VERCEL_ENV` with no override — an explicit switch is occasionally needed (e.g. verifying
  Resend from a preview deployment) and mirrors Feudo's `EMAIL_PROVIDER` more closely than the
  original ADR argued for, while keeping the safe default. Regardless of the switch, `capture` is
  refused when the database host exactly matches the production Neon pooler host, so a
  misconfigured `MAILER=capture` can never run against production data.
- `buildAuthOptions(db, env, mailer)` takes the mailer as a constructor argument (default
  `getMailer(env)`), so unit tests can inject `FakeMailer` without touching a database or the
  `VERCEL_ENV`/`MAILER` env resolution — this **supersedes** an earlier shape where `FakeMailer`
  existed but nothing wired it in.
- The E2E-only route (`/api/e2e/verification-link`) still requires `E2E_SECRET` and a
  non-production deployment, but now compares the header against the configured secret with
  `crypto.timingSafeEqual` (`timingSafeEqualStrings`, a sibling module the route imports so
  `route.ts` exports only the Next.js route contract Next's typed routes require) — byte-length
  checked first, since a naive `.length` comparison uses UTF-16 code units, which can match for
  two strings whose UTF-8 byte lengths differ (a multibyte header), and `timingSafeEqual` throws
  on a byte-length mismatch instead of returning false; that throw would have produced a 500,
  telling an attacker their guess had the right character count. Every rejection path (missing
  secret, production, wrong byte length, wrong value) returns the same 404, so neither a timing
  nor a response-shape difference can help an attacker guess the secret or distinguish "wrong
  secret" from "not configured". `findLatestVerificationLink(db, email)` is the single
  implementation of "read the latest captured link for an email", used by this route (through
  `readE2EVerificationLink`, the only Better Auth-module export the route needs beyond
  `isProductionDeployment` / `readE2ESecret` — the route imports exclusively from
  `@/modules/auth`) and by
  `service.integration.test.ts` — no second copy of the link-extraction regex.
- `authRouteHandlers` (`src/modules/auth/auth.ts`) is the one Next.js Route Handler the module
  exports, from its index; `app/api/auth/[...all]/route.ts` re-exports it and imports nothing else
  from the module, keeping the module's index its sole entry point.
- `src/modules/auth/service.ts` uses one calling convention for Better Auth throughout —
  `getAuth().handler(request)` (a synthetic HTTP request), not `auth.api.*` — because Better
  Auth's rate limiter runs only inside the router's `onRequest` hook, which `auth.handler()`
  triggers and `auth.api.*` bypasses entirely; calling `auth.api.*` anywhere in this module would
  silently exempt that call from rate limiting. The handler path is therefore required both for
  today's `429 → rate_limited` mapping (every outcome this module returns —
  `invalid_credentials`, `email_not_verified`, `rate_limited`, … — is derived from a real HTTP
  status code and a JSON error `code`, where `auth.api.*` throws `APIError` on failure instead of
  returning a `Response`, needing a second, separate mapping) and for ticket #10, which turns rate
  limiting on. This includes sign-out, which the original implementation called through
  `auth.api.signOut` alone.
  **Fix-forward on ticket #9's review pass (this same date)**: the `nextCookies` plugin
  (`options.ts`) never fires for this call path — its `after` hook bails out whenever
  `ctx._flag === "router"`, the flag Better Auth's own router sets while running
  `auth.handler()` — so the session `Set-Cookie` from a successful sign-in, sign-up or sign-out
  was computed but never reached the browser. `callAuthHandler` now forwards it itself, parsing
  the response's `Set-Cookie` with `better-auth/cookies`' own `parseSetCookieHeader` /
  `toCookieOptions` and writing it through Next's `cookies()`, swallowing the "outside a request
  scope" case exactly like the plugin's own hook does. The same pass also closed a gap where the
  raw `/sign-up/email` endpoint's `hooks.before` gate checked `termsAccepted` but not
  `privacyAccepted` — a direct POST past the UI form could accept the terms and skip the privacy
  policy; the gate now requires both, still recorded as the one `termsVersion`/`termsAcceptedAt`
  pair (LGPD requires both accepted together, not two independently versioned artifacts) — and
  enabled the Drizzle adapter's `transaction: true`, wrapping a sign-up's `user` and `account`
  inserts in one `db.transaction()` so a failure partway through can never leave an orphan `user`
  row.

**CI database topology**

Two Neon projects, one per environment class, the same shape Feudo settled on:

- **The production resource** is connected to the Vercel **Production** environment only. Never
  reset, never touched by CI.
- **`fetha-preview`**, a separate, free Neon project, is connected to both Vercel **Preview** and
  **Development**, and is also the database CI uses — not a fresh branch per PR. The GitHub secret
  `DATABASE_URL_PREVIEW` points at it.
- CI's `ci` job resets and migrates `fetha-preview` on every run, as steps inside the same job
  (guarded by whether `DATABASE_URL_PREVIEW` is configured, checked once and exposed as a step
  output, since secrets cannot be read directly in an `if:`), not a second job: `pnpm --filter
@fetha/web run db:reset` (drops and recreates the `public` and `drizzle` schemas, cascading,
  wiping schema drift left over by any other branch) then `db:migrate` then `db:seed-structures`
  (`scripts/seed-structures.mjs`, an idempotent upsert on the structure catalog's primary key, so
  a catalog edit ships by editing the script and letting the next migrate run reseed it) then
  `pnpm --filter @fetha/web run test:integration`. `db:reset` (`scripts/reset-database.mjs`)
  refuses to run — before issuing any query — unless the host of `DATABASE_URL` exactly matches
  the `fetha-preview` pooler host or `ALLOW_DISPOSABLE_DATABASE=1` is set explicitly, and refuses
  unconditionally, even with that override, when the host exactly matches the production pooler
  host (`scripts/lib/database-guard.mjs`, `assertDisposableDatabase`). The same guard binds
  the integration suite (`vitest.integration.config.mts`, so a single file run with
  `vitest --config` directly is refused too) and, through `assertWritableDatabase`, `db:migrate`
  (`scripts/migrate-database.mjs`), `db:seed-structures` and `seed-invite.mjs`, after two
  implementers migrated and tested against another project's database inherited from the shell
  (#49). The last three reach production only with `ALLOW_PRODUCTION_DATABASE=1`, which
  `migrate-production.yml` sets (and the owner, by hand, for an invite) and which is refused for
  any host other than the production one. These scripts overlay `apps/web/.env.local` (from
  `vercel env pull --environment=preview`) on the inherited environment, file winning, because
  Next.js and dotenv let a variable already exported in the shell win over the file. `pnpm dev` (`scripts/dev.mjs`) applies the same overlay and
  `assertDisposableDatabase` before starting Next.js, when a `DATABASE_URL` is set at all (#102). Both hosts are Neon's opaque
  per-endpoint pooler hostnames (e.g. `ep-lively-mode-…`), unrelated to either project's name —
  confirmed with `vercel env pull` against both environments, not assumed — so the guard is an
  exact match against a known/configured host, not a substring "marker" on the project name; the
  preview host has a safe-by-default fallback baked into the script, overridable through the
  `DATABASE_RESET_ALLOWED_HOST` GitHub Actions variable (a hostname, not a secret) the same way
  Feudo's `DATABASE_RESET_ALLOWED_HOST` works. Because the database is reset
  every run, integration tests' own row cleanup (`src/db/test/cleanup.ts`) is a courtesy for local
  runs and interleaved test files, not what tenant isolation or test independence relies on; a
  cleanup failure is logged and swallowed rather than failing the test that already asserted what
  it needed to.
- **Production is migrated by a separate workflow**, `migrate-production.yml`, triggered on push to
  `main` only, `concurrency: { group: migrate-production, cancel-in-progress: false }`, running
  `pnpm --filter @fetha/web run db:migrate` then `db:seed-structures`, both with
  `DATABASE_URL: secrets.DATABASE_URL_PRODUCTION` and `ALLOW_PRODUCTION_DATABASE=1`.
  It is lean — install, migrate and seed, no build — because `apps/web/vercel.json`'s `buildCommand` no
  longer runs a migration itself (`pnpm build` only); Vercel's own build must never be the thing
  that mutates the production schema, since a build can run for a preview or be retried.
- **No per-PR Neon branch.** This deviates from Feudo's stated preview-branch-per-PR plan in
  `CLAUDE.md`'s Stack section (updated alongside this ADR) for the same reason Feudo itself ended
  up sharing one long-lived preview project: it is free, and correctness comes from resetting the
  schema every run, not from isolating it per PR.
- **Every migration merged to `main` must be expand/contract, compatible with the previously
  deployed code.** `migrate-production.yml` (push to `main`) and Vercel's production deploy both
  trigger off the same push and run concurrently, with no ordering guarantee between them: a
  migration can apply before, during or after the new code goes live, and the _previous_ code
  keeps serving traffic for however long the deploy takes either way. A migration on `main` may
  therefore only add (a nullable or defaulted column, a new table, a new index) or keep an
  existing shape queryable by code that does not yet know about the change; renaming or dropping a
  column, tightening a constraint, or any other change the previous release cannot tolerate must
  be split into an expand release (ship the new shape, keep the old one working), a code release
  that stops using the old shape, and a contract release (drop the old shape) — never one
  migration that does both. This governs `main` only; the preview database is reset from an empty
  schema on every CI run (above), so no such ordering constraint applies to migrations still in a
  PR.

## Considered options

- **Better Auth's `organization` plugin, mapped to nothing** (Feudo's shape unchanged): rejected;
  Fetha has no concept a household or org would model, and carrying unused membership tables and
  role checks would violate YAGNI for no benefit.
- **Terms acceptance as only a separate history table, never a Better Auth field** (this ADR's
  original decision, and Feudo's choice): rejected on revision; it made the terms consent
  eventually-consistent with the user row (`after` hook, two statements, not one), which meant a
  registration could in principle succeed with a user who never durably accepted anything if the
  second write failed. Keeping the table for history but moving the source of truth onto the user
  row closes that gap while keeping the diffable history.
- **A fresh Neon branch per PR for integration tests**: rejected for the same reason Feudo rejected
  it — branch-per-PR costs money past the free tier and adds a branch-lifecycle step to every CI
  run; a shared project reset every run is free and gives the same "start from a clean schema"
  guarantee.
- **`EMAIL_PROVIDER`-only env switch with no `VERCEL_ENV` default** (Feudo's original choice):
  rejected in favor of defaulting from `VERCEL_ENV` with an explicit override, since "capture
  instead of send" must be true for every non-production deployment by default, not opt-in per
  environment, while still allowing a deliberate preview-time check of the real Resend path.

## Consequences

- Better Auth's vocabulary (`user`, `session`) appears in `src/db/schema/auth.ts` and `options.ts`
  only; the rest of the app imports `CurrentUser` from `src/modules/auth`.
- "Every domain table carries `user_id`" (CLAUDE.md) holds without exception here; `invites` and
  `mail_outbox` are operational, system-written mechanism, not user data, so neither carries one.
- Every `timestamp` column in this ticket's schema is `timestamp with time zone`; Postgres stores
  UTC internally either way, but an app that ever runs outside UTC (a developer's machine, a
  future non-UTC deployment) would silently misread a timestamp-without-time-zone column.
- Magic link, password reset and rate limiting shipped in ticket #10 (ADR-0018): they add plugins
  and hooks to `options.ts` and one operational table (`rate_limits`), without touching the
  repository pattern established here.
- Follow-ups filed as issues by the orchestrator, deliberately not in this ticket: token-based
  invites (today's invite is keyed by email only, with no secret token in the link — acceptable at
  single-digit-user scale but not a pattern to grow); purging unverified users (an account that
  never verifies its email is never deleted today).
